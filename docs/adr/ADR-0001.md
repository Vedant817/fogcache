# ADR-0001 — Monorepo and service decomposition

Status: Accepted · Date: 2026-08-07 · Issue: VED-54

## Context

FogCache spans seven runtime services, one admin web app, a Python training pipeline, shared contracts, and an integration test suite. We need one source of truth for builds, versions, and cross-service changes while keeping independent deployability.

## Decision

Use a single Git repository with Maven multi-module layout (`fogcache-bom`, `fogcache-common`, `fogcache-contracts`, one module per service, `fogcache-integration-tests`) plus `fogcache-admin-web` (Next.js) and `fogcache-model-training` (Python) as sibling directories with independent toolchains. Services communicate only through `fogcache-contracts`.

## Alternatives considered

- Per-service repos: rejected — cross-cutting contract changes (Kafka events, gRPC) would require synchronized releases.
- Single "everything in one module" app: rejected — violates independent scaling of edge vs control plane.

## Consequences

+ Atomic cross-service changes and one-command CI. + Contract-first enforced structurally.
− Large repo; mitigated by module boundaries and `.gitignore`d generated code.
− Coupled build; mitigated by Maven `-pl` reactor targeting and CI per-module jobs.

## Rollback/migration

Extraction path: move a module directory to its own repository and add a Git submodule/packaged dependency; contracts stay in `fogcache-contracts` published to a local repository manager.
