# ADR-0002 — Reactive request path (Spring WebFlux / Netty)

Status: Accepted · Date: 2026-08-07 · Issue: VED-54

## Context

Edge nodes must sustain high concurrency (2,000 in-flight) with low tail latency while coordinating single-flight loaders, disk I/O, and origin HTTP calls — all I/O-bound, latency-sensitive work where thread-per-request blocking scales poorly.

## Decision

Adopt Spring WebFlux on Reactor Netty for the edge, routing, and analytics services' request/event paths. Blocking disk (RocksDB) and SDK calls are isolated on bounded `boundedElastic` schedulers with explicit backpressure; Caffeine lookups stay on the event loop (non-blocking). Service-to-origin calls use the reactive `WebClient`.

## Alternatives considered

- Spring MVC (thread-per-request): rejected for the edge — 2,000 in-flight × blocking IO would need ~2,000 threads/node; tail latency under load degrades.
- Vert.x: rejected — Spring ecosystem consistency with control/analytics services outweighs marginal throughput.

## Consequences

+ High concurrency with bounded threads; reactive backpressure to Kafka producers. + Consistent WebClient/Security model across services.
− Reactive debugging/stack traces are harder; mitigated by structured logs + trace IDs.
− Some libraries are blocking-only (RocksDB, ONNX Runtime); contained by isolation schedulers and measured saturation (golden signal).

## Rollback/migration

Request-path abstraction behind service interfaces; a blocking adapter (MVC + `CompletableFuture`) can be swapped in for a service without contract changes. Perf gates in milestone 12 decide if the reactive path is retained.
