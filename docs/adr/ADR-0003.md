# ADR-0003 — Memory tier (Caffeine) and disk tier (RocksDB)

Status: Accepted · Date: 2026-08-07 · Issue: VED-54

## Context

The edge cache engine needs a fast memory tier with configurable LRU/LFU policy, plus a durable disk tier for large objects and restart recovery. Caffeine provides high-performance in-memory caching; RocksDB provides an embedded LSM key-value store with restart recovery.

## Decision

Memory tier: Caffeine behind a project-owned `CachePolicy`/`CacheStorage` interface exposing LRU, LFU, and a recommended TinyLFU admission mode (one-hit-wonder protection) while keeping LRU/LFU comparability. Disk tier: RocksDB storing payloads + entry metadata for demoted and large objects, keyed by normalized key hash with generation tombstone checks. The interface is pluggable so a policy or storage implementation can be replaced without touching request handling.

## Alternatives considered

- Custom in-memory maps with hand-rolled eviction: rejected — eviction correctness under concurrency is subtle; Caffeine is battle-tested.
- H2/SQLite disk: rejected — lacks LSM write characteristics for 500 GB class workloads.
- Redis-backed cache: rejected as primary tier — correctness must not depend on a network hop in the request path (Redis remains coordination-only).

## Consequences

+ Proven memory tier with windowed admission; durable disk tier with crash recovery. + Policy comparability for milestone 06 gates.
− RocksDB C++ dependency (managed via JNI artifact); sizing/compaction tuning needed.
− Two storage systems to back up/recover; mitigated by entry-level checksums and recovery tests.

## Rollback/migration

Storage interface allows memory-only mode (disk tier disabled) and policy swap via configuration. RocksDB data dir is disposable by design (cache is not a source of truth); invalidation/version rules in `replication-semantics.md` prevent stale resurrection after recovery.
