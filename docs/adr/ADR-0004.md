# ADR-0004 — Source-of-truth split: PostgreSQL, Redis, Kafka, S3

Status: Accepted · Date: 2026-08-07 · Issue: VED-54

## Context

Four infrastructure systems are involved. Conflicting "source of truth" claims between them are the main correctness risk (e.g., config in Redis but audited in PostgreSQL, or cache metadata in Kafka).

## Decision

| System | Responsibility | Source of truth for |
|---|---|---|
| PostgreSQL (Flyway) | Control service configuration + audit | tenants, origins, policies, quotas, admin audit trail |
| Redis (Redisson) | Ephemeral coordination | node health leases, emergency cross-node single-flight fallback, idempotency keys (TTL-bounded) — never durable state |
| Kafka | Event backbone | access, invalidation, replication, classification, placement, prefetch, audit **events** (ordered streams, retention-bounded) |
| S3-compatible (MinIO local) | Object storage | content service payloads; edge disk tier is not a source of truth |

Rules:
- Cache content is **never** a source of truth; the origin (content service) is.
- No system owns what another owns: config/audit → PostgreSQL only; coordination → Redis only; event ordering → Kafka only; payloads → S3 only.
- Cross-system consistency (e.g., invalidation) is achieved via generation numbers and idempotent event processing (`replication-semantics.md`), never by multi-system transactions.

## Alternatives considered

- Config in Redis for speed: rejected — loses auditability; control-plane reads are low-rate.
- Kafka as durable config store: rejected — wrong access pattern for point queries.

## Consequences

+ Clear ownership; single system to migrate/restore per concern. + Correctness independent of Redis availability.
− Eventual consistency between systems is explicit and testable (convergence SLOs).

## Rollback/migration

Each system is swappable behind an interface: PostgreSQL→any SQL DB (Flyway-compatible), Redis→another KV (lease semantics preserved), Kafka→another broker (ordered topics preserved), S3→any S3-compatible store.
