# ADR-0005 — REST versus gRPC boundaries

Status: Accepted · Date: 2026-08-07 · Issue: VED-54

## Context

FogCache has external APIs (clients, operators, browsers), internal node-to-node operations (transfer, probe, repair), and control-plane APIs. Choosing one protocol for everything would burden one side or the other.

## Decision

- **REST/HTTP (OpenAPI-first)** for every boundary that is external or has human-facing semantics: edge data plane (`GET/HEAD`), routing control (`resolve`, `register`, `heartbeat`, `drain`, `topology`), and admin APIs (tenant/origin/policy/quota/key-action/node/analytics/model).
- **gRPC (Protobuf-first)** for low-latency node-to-node and stream-heavy internal operations: metadata lookup, object transfer (streaming), invalidation generation push, probe, repair, prefetch request/outcome.
- A debug HTTP bridge for gRPC services is permitted in local/CI only (gRPC-Web is avoided in v1).

## Alternatives considered

- All-gRPC including external APIs: rejected — browsers, curl, and CDN-facing clients expect HTTP caching semantics; Vary/conditional requests are HTTP-native.
- All-REST including transfer: rejected — streaming large-object transfer and high-rate probes favor gRPC.

## Consequences

+ Right protocol per boundary; OpenAPI + Protobuf contracts live in `fogcache-contracts` and generate stubs. + External consumers get standard HTTP semantics.
− Two contract ecosystems to maintain; mitigated by shared conventions doc (`contract-conventions.md`) and codegen in CI.

## Rollback/migration

Interfaces are versioned (`/v1`, proto package `fogcache.internal.v1`). A boundary can migrate protocols behind the same contract while a version is live; deprecated versions are removed only per compatibility rules in `contract-conventions.md`.
