# ADR-0006 — Consistent-hash ownership model

Status: Accepted · Date: 2026-08-07 · Issue: VED-54

## Context

Edge nodes join, leave, and fail. Object placement must minimize remapping, support capacity weighting, produce ordered fallbacks, and never depend on a single coordinator in the request path.

## Decision

- A consistent-hash ring with configurable virtual nodes (baseline 160/node) owned by the routing service.
- Membership filtered by lease validity, readiness, drain state, protocol compatibility, and tenant eligibility.
- Node weight = usable cache capacity with safety limits (movement dampening) to prevent oscillation.
- Lookup yields primary + ordered fallback candidates; keys stay with the same owner while the ring is unchanged.
- Topology snapshots are versioned; clients (edges/gateway) cache the snapshot and continue serving during control-plane interruption.
- Graceful drain: node stops receiving new ownership before shutdown (J-01 variant E1).
- Remap bound: ≤ 20% of keys move when one node of a 9-node cluster fails (capacity model assumption; property-tested).

## Alternatives considered

- Centralized key→node table (PostgreSQL/Redis): rejected — every miss would hit the coordinator; single point of failure in the request path.
- Rendezvous hashing: viable, but consistent hash with virtual nodes has a larger proven ecosystem for capacity weighting; kept as ADR follow-up if movement bounds fail load tests.

## Consequences

+ Bounded remapping, capacity weighting, ordered fallbacks, no request-path dependency on coordination. 
− Movement statistics must be exposed before membership changes are applied (topology API + dry-run resolve).
− Ring correctness is property-tested (bounded remap, balance, stability) in milestone 04.

## Rollback/migration

The ring algorithm is isolated behind `HashRing` interface; swapping to rendezvous hashing only changes routing-service internals and topology versions. Membership can be pinned to static config in emergencies (kill switch).
