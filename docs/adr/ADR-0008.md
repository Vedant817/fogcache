# ADR-0008 — Kubernetes deployment topology

Status: Accepted · Date: 2026-08-07 · Issue: VED-54

## Context

Production must run on Kubernetes with regionally distributed edge nodes, independent scaling, automated delivery, and reliable failure behavior — while the local environment stays simple (Docker Compose).

## Decision

- **Local/CI:** single `compose.yaml` per service plus a root compose stack (PostgreSQL, Redis, Kafka, MinIO, Keycloak, LGTM telemetry) — no Kubernetes required for development (milestone 02).
- **Production (Kubernetes, milestone 13):**
  - Edge: regional Deployment (or DaemonSet where node pinning is required), replicas per region, anti-affinity across nodes/AZs, PodDisruptionBudgets, HPA on CPU + cache-occupancy metrics.
  - Routing/control/analytics: Deployments with HPA; routing as a stateless service (ring state in Redis leases + local snapshot).
  - Stateful systems: managed equivalents preferred (PostgreSQL, Redis, Kafka, S3-compatible object storage); operators only where managed services are unavailable.
  - Network policies (service mesh identity for internal traffic), sealed secrets (SOPS/External Secrets), image signing, OCI artifact scanning.
  - Delivery: GitOps with Argo CD from tagged Helm charts; Terraform for infrastructure; rolling updates with readiness gates; rollback = previous chart revision (≤ 15 min).
- Edge disk tier uses StatefulSet-local PVCs (ephemeral acceptable — cache is disposable by design, per ADR-0004).

## Alternatives considered

- Docker Swarm/Nomad: rejected — ecosystem and managed-service fit weaker; team targets GitOps on Kubernetes.
- Serverless edge: rejected — long-lived disk tier and in-process state conflict with ephemeral functions.

## Consequences

+ One production platform with standard tooling; independent scaling of data vs control plane.
− Kubernetes operational complexity; mitigated by reproducible local env, runbooks (milestone 14), and automated delivery.

## Rollback/migration

Helm chart + Argo CD revision pinning provides image/schema/config rollback; a compose-based fallback deployment exists for disaster recovery until single-cloud reliability is proven (non-goal: multi-cloud active-active).
